# Bloque 6 (usuarios, historial y zona de peligro) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** El administrador puede eliminar usuarios sin emitidos (conservando su nombre en lo que escribieron), filtrar el historial y borrar todos los presupuestos; más los arreglos menores de Configuración, PDF y notas.

**Architecture:** Las cuatro tablas con autor ganan una columna de nombre **que solo se rellena al eliminar al usuario** (FK opcional con `SetNull`); `deleteUser` copia el nombre y borra en una transacción. `listAudit` amplía su filtro y la página usa un formulario GET que se envía solo. `deleteAllQuotes` hace `TRUNCATE "Quote" CASCADE` y borra contadores e historial de presupuestos; después, `DATA_DIR/pdf`.

**Tech Stack:** Next.js 16, React 19, Prisma 7, Zod 4, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-18-bloque-6-design.md`. Maqueta: `docs/diseno/maquetas/bloque-6.html` (Usuarios; Historial variante B; Zona de peligro variante B).

## Cambio respecto al diseño (ponytail ultra, a confirmar por el usuario)

El diseño (6.2) pide rellenar el nombre en la migración y escribirlo en **cada alta**. Eso obliga a tocar las ~25 llamadas a `logAction` y las altas de notas y ajustes. Este plan lo escribe **solo al eliminar al usuario** (`UPDATE … SET userName = nombre WHERE userId = id` justo antes del `DELETE`). Resultado visible idéntico: mientras el usuario existe se muestra su nombre por la relación; al eliminarlo queda el nombre copiado. Migración sin `UPDATE` de datos. Diferencia: si un usuario cambiara de nombre, se ve el último (hoy no se pueden renombrar usuarios).

## Global Constraints

- Código en inglés; interfaz y documentación en español. Permisos siempre en el servidor. Formularios con `ActionForm`/`RowForm`; confirmaciones con `ConfirmButton`.
- Lo emitido no se modifica (la dirección de las instantáneas viejas sale como era).
- Pruebas: `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION="Autorizo el reset (Recomendado)" pnpm test`. Tras migrar: `pnpm exec prisma generate` y reiniciar `pnpm dev`.
- Migración escrita a mano en `prisma/migrations/20261118140000_author_names/migration.sql`.
- **Cada tarea sube la versión de `package.json`** (1.6.1, 1.6.2, 1.6.3, 1.6.4) y termina con commit y `git push origin mejoras-uso-real` (`:3101` lo recoge). Archivos CRLF: `git -c core.autocrlf=false add`.
- Fusionar en `master` o desplegar producción exige el visto bueno del usuario.
- Textos exactos: «Notas internas» · «¿Eliminar a {nombre}? Sus N borradores pasarán a ti» · «N emitidos» · «{nombre} (eliminado)» · «Sistema» · «Más filtros (N activos)» · «Quitar filtros» · «Zona de peligro» · «Borrar todos los presupuestos…» · «¿Borrar los N presupuestos?» · «Escribe BORRAR para confirmar».

## Review Focus

- Eliminar a alguien que tiene un borrador que es revisión de un emitido ajeno: el borrador pasa al admin y nada falla → prueba en Tarea 2.

- Filtro `hasta` = hoy con una entrada a las 23:30 de Madrid (día UTC siguiente) → aparece → prueba en Tarea 3.
- Borrar todos con revisiones encadenadas (`parentId`, `supersededById`) y documentos emitidos → no lo impide ninguna FK → prueba en Tarea 4.
